HybridCLR · product brief from an R&D spike

Shipping live-ops without waiting for a store release

An R&D spike on a production-sized Unity mobile game proved that it can download and run new live-ops code on Android the same way it already downloads art. This brief, written for a product discussion, says what that is, how well it works, what it is good for and what it cannot do.

1. What it is, in one picture

A Unity mobile build is frozen the moment it goes to the stores. Art and config can change afterwards because they already go through a content pipeline (Addressables). Behaviour cannot. Any change to how a screen works, however small, waits for the next store build and then for players to update.

The spike adds one capability: the app can also download small pieces of game logic from the game's own CDN, written in the same C# the developers already use, and run them. The technology is an open-source Unity add-on called HybridCLR. Players never see it. To them it is the same as an event appearing in the lobby.

The rule set for it. Hot code never touches core game logic (matches, economy, purchases, login). It is for live-ops only: event screens, lobby widgets, promotional flows, and fixes to those. Each live-ops feature opts in explicitly; everything else stays exactly as it is in the store build.

3. Success rate: how proven is this?

In the industry

HybridCLR is free and open source (MIT licence) and has been public since 2022. Its maintainers state, on the project's own page, that "thousands of commercial game projects have integrated HybridCLR, with over a thousand already launched on the App Store and Google Play" and that "nearly a hundred games in the top 500 free iOS chart use HybridCLR". These are the project's own claims, not independent figures, and the user base is heavily Chinese: most of the public write-ups, forums and case studies are from Chinese studios, and part of the documentation is Chinese first.

The honest reading: the runtime is mature and widely shipped, including on iOS by many studios. What is thin is Western public precedent and any statement from Apple or Google naming it. Section 4 shows the named titles; section 10 covers what that does and does not prove.

In the spike

  • Every planned experiment worked on the first device run after the build was correct. The failures during the spike were all in tooling and pipeline setup (a wrong label, a stale package, a CI job that had not published yet), each costing one rebuild. None were runtime crashes in downloaded code.
  • The debug build with the hot runtime in it behaved like any other dev build in day-to-day use. Performance was not measured formally; the kind of code this is for (UI and event flow) is not performance sensitive.
  • Not done: a Google Play upload, a large-audience test, iOS, or a production-signed build. See section 12.

5. Product advantages

Events on the live-ops calendar, not the release train

  • A new event popup or lobby activity can go live on a chosen date, independent of when the next client ships.
  • Seasonal or one-off events no longer need to be designed months ahead to make a build cut.

Fix live-ops problems in hours

  • A wrong rule, a broken flow or an off-brand screen in an event can be patched the same day, or switched off with a kill switch.
  • Players on old client versions get the fix too, as long as that version is still supported. Today they only get it if they update.

Experiment faster

  • Variants of an event's logic (not just its numbers) can be published and compared without a client release.
  • A feature that under-performs can be pulled instantly rather than living in the build until the next release.

Less dependence on update adoption

  • Fewer "wait for 80% adoption before the event starts" conversations.
  • Fewer forced-update prompts for live-ops reasons.
Scope reminder. This is for live-ops content and flow. It does not make match rules, economy or store changes hot. Those keep the release train.

6. Developer advantages (and costs)

Wins

  • Same language, same tools. Developers write ordinary C# and ordinary Unity prefabs. There is no second scripting language (Lua or JavaScript) to learn, debug or maintain.
  • A cleaner codebase as a by-product. To make features downloadable they must talk to the core through a small, stable contract. That modularity is worth having even if a hot update never ships.
  • Smaller QA surface per change. A patch is one feature's package, not a full client regression.
  • Rollback is trivial. Republish the previous package, or remove it.

Costs

  • Seams must be planned. A shipped feature can only be hot-fixed where it was built with a hook. Unplanned code cannot be patched. This is design work before each release.
  • New build steps in CI, and a per-client-version artefact to publish with every store build.
  • Two release processes. A hot release needs its own review, QA and sign-off, treated as seriously as a client release.
  • Some new host capability still needs a build. When a hot feature needs a door the core does not have yet (a new server endpoint, auto-popup scheduling), that door ships in a client release first. Features then flow through it without further builds.

7. Player advantages

  • No store update to get the event. It is just there next time they open the app.
  • Fewer forced updates and fewer broken events. Fixes arrive silently.
  • Smaller app. Over time live-ops features move out of the base install and download on demand, which also helps store listing size.
  • Negligible extra download. The code for a feature is tens of kilobytes; the art is the same art that would have shipped anyway.

Nothing changes for players who are offline: the app works as installed, and downloaded features appear once they are online, exactly as downloaded art does today.

8. What it cannot do

This section exists so nobody comes away thinking "any bug can be fixed without a release". It can't.

  • It cannot change code that is already in the shipped app. It can add new code, and it can steer shipped features through the hooks they were built with. A bug in code with no hook needs a store build, as today.
  • Core game logic is out of scope by rule. Matchmaking, gameplay rules, currencies, purchases, login. Both because of policy risk and because it is the wrong tool.
  • Startup crashes, native plugins and engine-level issues are untouched. If the app cannot reach the lobby, nothing downloads.
  • Only features that opted in can be hot-fixed. Opting in is a release-time decision per feature.
  • Server changes still need the server. Hot code can read and send the same things the client can today; new server messages still land in a client release first.

The paid editions change the first bullet

Everything above describes the free community edition, which is what the spike used. The maintainers sell three paid editions, licensed per project as a one-off purchase with two years of support and updates. Prices are not published; they are quoted on request from a company email address.

Why the spike did not start there. Three reasons:

  • Policy exposure grows. Replacing functions inside the shipped app is the most literal reading of what Apple's 2.5.2 forbids, and the hardest to defend under Google's interpreter exemption. The community edition's "add code through planned hooks" is the more defensible shape.
  • Cost and lock-in are unknown. Per-project licence, two-year term, one small vendor, price on request. The free edition can be removed from a project in an afternoon; a product built around Differential Hybrid Execution cannot.
  • It still does not fix everything. Startup crashes, native plugins, engine behaviour and server contracts are untouched in every edition. Core game logic stays out of scope by rule either way.
Recommendation: prove the free edition in production first. If after a pilot the hooks prove too limiting, request a quote for Ultimate and evaluate it on a branch.

9. How a live-ops problem gets fixed: the ladder

Each rung is cheaper and faster than the one below it. The spike proved rungs 2 and 3. Rungs 0 and 1 are standard practice already.

Server config. Numbers, dates, on/off flags, text. Minutes, no client involvement.

11. iOS: the strategic question

Technically the same mechanism works on iPhone. Policy-wise it does not, and the downside is the account, not one build. So the proposal is:

Android: hot

Live-ops features and fixes download on Android. One pilot feature first, with the safeguards in section 10.

iOS: same code, baked in

The same feature code is compiled into the iOS build. iOS players get the feature with the next release; nothing is downloaded. One codebase, two delivery modes.

Two alternatives were checked and are not shortcuts:

  • "Use JavaScript instead, Apple allows that." Apple allows scripts run by its own engine only. The Unity JavaScript options bundle their own engine, which puts them in the same position as HybridCLR. A policy-clean JavaScript route would be a separate, unproven project.
  • Data-driven event templates (generic event screens configured by server data) are the only route that is both industry-standard and policy-free, on both platforms. They cover events that fit a template, and nothing else. They are rungs 0 and 1 done thoroughly, and they are complementary to this work, not a replacement.
Whether to ever hot-update on iOS is a business decision, with the account risk stated above. The engineering recommendation is no.

Hotfixing existing features has an extra prerequisite: each feature needs its hooks added in a store build before it can be patched. That is per-feature work and should be prioritised by how often each feature needs live-ops changes.

Quick answers

Will players notice anything?

No. A feature appears, or a fix lands, on the next app open. Same as downloaded art.

Does the app get bigger?

The runtime adds a small amount to the install. Over time the app gets smaller as live-ops features move out of the base build.

What if a package is broken?

The app skips it and runs without it. The package is pulled or replaced on the CDN. Players are never stuck.

Does this replace server-driven config?

No. Config stays the first tool for every change that is a value. This is for changes that are logic or screens.

Did any of this ship?

No. It was research: dev-signed test builds only. Nothing was submitted to either store.
